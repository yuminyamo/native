障害ログAI調査ガイド

ログを丸ごとAIに読ませるのではなく、機械的な処理で「証拠」を絞り込んでから渡し、足りない部分はAI自身に取りに行かせる。この考え方を4つの案に分け、架空の障害例を使って具体的に説明します。

作成日 2026-10-04改訂 2026-10-05対象：障害一次調査の自動化（チケット書き戻し）の拡張

全体像

4つの案は独立した選択肢ではなく、1つのパイプラインの部品です。

案役割着手しやすさ主な効果
案1 ダイジェスト生成AIへの最初の入力を数千トークンに圧縮し、同じ環境の平常期間と比べて「今回だけの変化」を目立たせるすぐ着手できる（スクリプトのみ）コンテキスト削減、ノイズ除去、再現性、少しずつ進む障害の発端の発見
案2 ログ検索ツールダイジェストで足りない部分をAIが自分で取りに行く案1の後（ログのDB化が前提）見落とし防止、時間窓の外も調べられる
案3 環境をまたぐ知見再現環境のログとソースコードから既知ノイズ辞書を作り、「いつも出ているログ」を下に回す再現環境のログが手に入り次第（リリース時など）どの顧客の障害でも使えるノイズの知見を、人のレビューなしで貯める
案4 ログ自体の改善相関IDや構造化で、ログを機械が辿りやすくする改修の機会に継続的に長期的な調査効率、ツールの単純化

説明に使う障害例

以降の具体例はすべてこの1件の架空の障害を使います。ログ形式、ID、顧客名も説明用に作ったものです。

障害チケット INC-2026-0931架空の例
顧客・環境A社 / PMS 5.2.3 / Windows Server 2019 / 印刷サーバ1台
症状9月30日 10時40分頃から、一部ユーザーの印刷ジョブがプリンタで出力されない。管理画面ではジョブが「保留」のまま残る。

真の原因（後で判明）一時ファイルの定期削除タスクが無効になっており、スプール領域が少しずつ埋まって容量が尽きた。

この障害を人が調べると、まず目につくのは大量に出ている LDAP referral ignored の警告や、障害後に急増するDB接続待ちの警告です。どちらも原因ではありません。前者は平常時から出ているノイズ、後者は結果として起きた二次症状です。ログ全量をAIに渡すと、AIも同じ罠にはまりやすくなります。

案1ログダイジェスト生成

LLMを使わないスクリプトで、ログ一式を「AIが最初に読む要約資料」に変換します。

処理の流れ

処理は次の順に進めます。どれも決定論的な処理なので、同じログからは常に同じダイジェストができます。テストもしやすく、AIの判断が揺れたときに入力側を疑わずに済みます。

  1. 収集と時刻の正規化：ファイルごとに異なる時刻形式・タイムゾーンをそろえ、1行を「時刻・レベル・コンポーネント・メッセージ」に分解する。
  2. 時間窓の切り出し：チケットの発生時刻の前後（例：±30分）だけを残す。窓は後で案2のツールから広げられる。
  3. マージ：複数ファイルを時刻順に1本へまとめる。サーバとエージェントの因果関係が並んで見えるようになる。
  4. エラー抽出と前後の文脈：ERROR／例外／スタックトレースを塊ごと抜き出し、前後数行を付ける。重なる範囲は1つにまとめる。
  5. テンプレート化と集計：Drain3で同じ形のメッセージをまとめ、「テンプレート × 件数 × 初出時刻」の表にする。テンプレート化は時間窓の中だけでなく全期間で行い、いつから出ているログかも分かるようにする。
  6. 平常時との比較：同じ環境の、正常に動いていたと思われる期間と比べる。日ごとの件数から「ある日から出始めた・消えた」ログ（変化点）を見つけ、平常期間の同じ時刻帯と件数を比べる（後述）。

顧客情報のマスキングは、ログを収集する段階で済ませておきます。案1に渡すログはマスキング済みとして扱い、ここでは行いません。

平常時との比較（平常プロファイル）

同じ環境の「正常に動いていたと思われる期間」と障害時を比べ、今回だけ変わったものを目立たせます。顧客ごとに使う機能の組み合わせや環境が違うので、比べる相手は他の環境ではなく、その環境自身の過去です。顧客はおよそ1ヶ月分のログを保存しているので、障害日だけでなくその前の日も含めて受け取ります（最低でも前営業日まで、できれば2週間程度）。

比較は2つの見方で行います。どちらもLLMを使わない決定論的な規則です。

  • 変化点：受け取った全日について、テンプレートごとの日別件数を数え、「ある日から出始めた（出現）」「ある日から消えた（消失）」を見つける。少しずつ進む障害は、障害日には原因のログが出ず、変化点にだけ現れることがある。
  • 平常期間との比較：正常だったと思われる日の、障害の時間窓と同じ時刻帯と件数を比べる。障害時だけ出たログだけでなく、障害時に消えたログも重要な手がかりになる。処理が黙って止まった場合はERRORが出ず、「いつもの完了ログが無い」ことでしか気づけないため。
変化点：テンプレートごとの日別件数（9/16〜9/30）架空の例
日付変化テンプレート変化の前変化の後
09-24（木）消失Temp cleanup finished: <NUM> files removed8/8日0/7日
09-24（木）出現Temp cleanup skipped: scheduled task disabled0/8日7/7日
09-28（月）出現Spool usage <NUM>% on <DRIVE>0/12日3/3日

「8/8日」は、その期間の8日のうち8日に出ていたという意味です。毎日3時に動く削除タスクの完了ログが9/24に消え、代わりにスキップのログが出始めています。案2の例でAIが最後にたどり着く原因を、ダイジェストの段階で直接指しています。

平常期間の選び方

平常期間は、規則で自動選択し、AIが確認して必要なら選び直します。

  • 規則：障害日より前の営業日のうち、最初の変化点より前で、ERRORが急増していない最も近い日を選ぶ。営業日はカレンダーではなく件数で判定する（国ごとの祝日や顧客ごとの休みを知らなくて済む）。
  • AIによる選び直し：障害内容・問い合わせ内容と照らして合わなければ、AIが期間を指定して作り直す。選んだ理由はダイジェストに残す。
  • ログの事実を優先する：問い合わせの「昨日までは正常」は手がかりであって事実ではない。その期間より前に変化点があれば、ダイジェストで警告する。

架空例では、前営業日の9/29ではなく、変化点（9/24）より前の9/23が選ばれます。9/29と比べると、削除タスクのスキップもスプール使用率の警告も両日に出ているので「変化なし」になり、原因を見逃すからです。受け取ったログの最初から変化点の後に見える場合は、さらに前のログを依頼するよう警告します。

実装のヒント

言語はPythonが扱いやすく、Drain3もDuckDBもPythonのライブラリとしてそのまま使えます。Drain3に渡すのは時刻やレベルを除いたメッセージ部分だけにするのがコツです。先頭に時刻が付いたままだと、すべての行が別物に見えてしまいます。

Drain3 の最小構成Python
from drain3 import TemplateMiner
from drain3.template_miner_config import TemplateMinerConfig

config = TemplateMinerConfig()
config.load("drain3.ini")          # マスキング規則（IP・パス・ジョブIDなど）を記述
miner = TemplateMiner(config=config)

for rec in records:                  # rec は時刻・レベル・メッセージに分解済み
    r = miner.add_log_message(rec.message)
    rec.template_id = r["cluster_id"]
# 集計：template_id ごとに件数・初出・最終時刻・レベルを数える

良い点

  • LLMを使わないので速く、費用もかからない
  • 同じ入力から同じ出力になり、テストできる
  • 既存の一次調査パイプラインの前段に足すだけで済む

限界

  • 抽出の段階で重要な1行を落とすことがある（案2で補う）
  • 平常期間の選び方を誤ると比較が役に立たない（規則の候補をAIが確認して選び直す）
  • 前の日のログが無いと平常時との比較ができない（ログ収集で期間を決めておく）

案2ログ検索ツール

ログ全量をDBに入れておき、AIが仮説に応じて必要な部分だけを問い合わせられるようにします。

ダイジェストは入口にすぎません。調査が進むと「この警告は障害の前から出ていたか」「同じジョブIDの他のログは何か」といった疑問が出てきます。人ならgrepやエディタで確かめるところを、AIにはツールとして渡します。コード・仕様・マニュアルを必要な時に必要な分だけ読む既存の一次調査と、同じ設計思想です。

ツールの例

汎用のSQLだけでなく、よく使う調べ方を専用ツールにしておくとAIが迷いにくくなります。どのツールも返す量に上限を設けるのが最も大事な点です。

ツール用途主な引数返却の上限
get_digest調査の入口。案1のダイジェストを返すticket_id約5,000トークン
search_logsキーワード・レベル・時間範囲・ファイルで検索query, level, from, to, file200行。超えたら件数と先頭20行のみ
get_context特定の行の前後を見るline_id, before, after前後それぞれ50行

具体例：AIの調査の進み方

架空の障害で、AIがツールを使って原因を確かめるまでの流れです。ダイジェストの変化点が指した「9/24」を手がかりに、時間窓（10:10〜11:10）の外にある証拠をAIが自分で取りに行っている点に注目してください。

  1. AI ダイジェストを読んで仮説を立てる

    最初の異常は10:42:05のスプール書き込み失敗（T07）。DB接続待ち（T12）はその後から増えているので結果側の可能性が高い。変化点によると、9/24から削除タスクの完了ログが消え、スキップのログが出始めている。容量不足がいつから進んでいたかを確かめ、9/24の変化と結びつくかを見る。

  2. ツール呼び出し
    search_logs(query="Spool usage", level="WARN", from="2026-09-27", to="2026-09-30 10:42")
→ 6件
09-28 03:00:12 WARN [spool] Spool usage 81% on D:
09-29 03:00:09 WARN [spool] Spool usage 88% on D:
09-30 03:00:10 WARN [spool] Spool usage 95% on D:
09-30 10:20:44 WARN [spool] Spool usage 99% on D:   … 他2件
  3. AI 仮説を更新する

    使用率が数日かけて単調に増えている。急な大量印刷ではなく、何かが消されずに溜まっている。毎日3時に動く処理を確認する。

  4. ツール呼び出し
    run_sql("SELECT ts, component, message FROM logs
         WHERE component = 'cleanup' ORDER BY ts DESC LIMIT 5")
→ 5行
09-30 03:00:01 cleanup  Temp cleanup skipped: scheduled task disabled
09-29 03:00:01 cleanup  Temp cleanup skipped: scheduled task disabled
… 09-24 以降すべて同じ
  5. AI 結論をチケットに書き戻す

    原因候補：一時ファイル削除タスクが9月24日以降無効になっており、スプール領域（D:）が枯渇した。
    根拠：cleanup の skipped ログ（9/24〜）、使用率の単調増加（81%→99%）、10:42:05 の disk quota exceeded。
    二次症状：ジョブ中断の再試行によるDB接続待ちの増加（T12）。
    次の確認：タスクが無効化された経緯（9/24前後の設定変更）、SpoolWriter.java:212 の容量不足時の扱い（コード参照）。

AIへの入力は、ダイジェスト約5,000トークンとツール結果4回分を合わせても1万トークン程度です。ダイジェストの変化点が示した「9月24日から」を、AIがツールで裏付けて結論にしています。

DuckDB にログを入れる

案1でパースしたレコード（全期間）を、そのままDuckDBのテーブルにします。サーバを立てる必要がなく、障害1件ごとに1ファイルのDBを作って捨てられるので、顧客ごとにログを分けて扱う運用にも合います。

取り込みと問い合わせの例SQL（DuckDB）
-- 案1で出力した JSON Lines（gzip）をそのままテーブルにする
CREATE TABLE logs AS SELECT * FROM read_json('INC-2026-0931/parsed/records.jsonl.gz');

-- 1分ごとの件数推移（count_by_time ツールの中身）
SELECT date_trunc('minute', ts) AS m, template_id, count(*) AS n
FROM logs
WHERE template_id IN ('T07', 'T12') AND ts BETWEEN '2026-09-30 10:30' AND '2026-09-30 11:00'
GROUP BY 1, 2 ORDER BY 1;

既存パイプラインへの組み込み方

  • まずは skills ＋ コマンドラインのスクリプト：既存の一次調査が skills でディレクトリ地図を渡しているのと同じ形で、「ログを調べる時はこのコマンドを使う」という skill を足すのが一番小さな変更です。
  • 複数の利用者・ツールから使うなら MCP サーバ：VS Code で個人が使う場合と、自動の一次調査の両方から同じツールを呼びたくなったら、MCPサーバとしてまとめると共通化できます。
  • 読み取り専用を徹底：run_sql は読み取り専用の接続で開き、タイムアウトと行数上限を必ず付けます。

案3環境をまたいで残す知見

障害ごとに捨てる顧客ログとは別に、再現環境とソースコードから、どの顧客の障害でも使える知見を作って残します。

案1との分担

同じ環境の平常期間との比較は、そのチケットのログだけで完結するので案1に含めます。案3が扱うのは、チケットや環境をまたいで残すものです。

案1 ダイジェスト生成案3 環境をまたぐ知見
入力顧客から受け取ったログ再現環境のログとソースコード
実行する時チケットごとリリース時、再現環境のログが手に入った時
出力障害対応の後に捨てる辞書として残す

他の顧客環境から貯めた統計は使いません。顧客ごとに使う機能の組み合わせや環境が違い、比べる基準にならないためです。顧客ログは障害対応が終われば削除するので、過去の顧客ログを後から集めることもできません。

既知ノイズ辞書

平常時から出ているWARN／ERRORを、理由と根拠付きでバージョンごとに登録します。案1は一致したログをダイジェストの下に回し、件数だけを1行で残します。長年の保守で担当者が頭の中に持っている「このエラーは無視してよい」という判断を、再現環境のログとソースコードから作り直す作業でもあります。

知見のある担当者がレビューする時間は取れない前提なので、人のレビューなしで作ります。作り方は次のとおりです。

  1. 正常期間のログを用意する：再現環境（検証環境）で、試験に合格した期間や障害を再現する前の期間など、正常に動いていたと分かっている期間のログを使う。再現環境は障害を再現する場所でもあるので、再現した期間は含めない。
  2. 候補を出す（スクリプト）：案1と同じ処理でテンプレート化し、正常期間に何度も出ていたWARN／ERRORを候補にする。
  3. 判断する（AI）：候補ごとに、AIがソースコードでログの出力箇所を探して前後の処理を読み、登録するかを決めて理由を書く。
  4. 登録する（スクリプト）：理由と根拠がそろっているかを検査してから辞書に反映する。登録しなかった候補も理由付きで残し、次から同じ候補を出さない。

AIが登録してよいのは、次のすべてを満たすものだけです。迷ったら登録しません。誤って登録すると本当の原因が下に回されて見落とされますが、登録しなければダイジェストに少し余計な行が残るだけで済むからです。

  • 出力箇所をソースコードで特定できた
  • ログを出した後も処理が正常に続き、結果に影響しない（代わりの手段で成功する、再試行で成功する、使っていない任意機能について知らせるだけ、など）
  • 顧客環境でも平常時に出うる（監視サーバが無い、試用ライセンスなど、再現環境に特有の条件で出るものではない）
  • 顧客環境で出たら設定ミスや異常の手がかりになるものではない
known_noise.yaml架空の例
- template: "LDAP referral ignored: <URL>"
  versions: ["5.2.*"]
  reason: "referral を無視して次のDCに問い合わせを続ける処理。認証の結果には影響しない"
  evidence:
    source: "再現環境 PMS 5.2.3 リリース試験 2026-09-16〜09-23"
    rate: "1時間あたり約12件（8日間で計2,304件）"
    code: "auth/LdapClient.java:340"
  generated_by: AI
  added: 2026-10-05

根拠（どの環境・期間のログか、平常時の件数、出力箇所）を必須にします。人が後から見直す時に、何を根拠に登録したかが分かります。

人のレビューがない分の安全策

  • 除外せず、下に回すだけにする：ダイジェストに件数を1行で残し、案2のツールでは通常どおり検索できる。
  • 今回だけ様子が違えば、ノイズ扱いをやめる：平常期間より急増した、平常期間に無かった、ある日から出始めた、のどれかに当たれば通常のログとして扱う。
  • 固定部分が短いテンプレートは登録しない：<*> failed のような項目は関係のないログまで一致してしまう。
  • バージョンで範囲を限る：出典と同じバージョン系列にだけ適用し、新しいバージョンでは再現環境のログから作り直す。
  • 顧客ログからは作らない：顧客環境は「正常だった」と確認できない。少しずつ進んでいた障害のログを平常と誤認するおそれがある。顧客環境ごとの平常時のノイズは、案1の平常期間との比較が扱う。

過去障害のシグネチャ（後回し）

解決済みの障害チケットに特徴的なテンプレートの組み合わせ（シグネチャ）を紐付けて貯め、新しい障害と照合する案です。年に10件程度の障害では蓄積が少なく、顧客ごとに使い方も違うため照合が当たる見込みが小さいので、後回しにします。始める場合は、既知ノイズ辞書と同じく案3の知見として残します。

案4ログ自体の改善

新機能や修正の機会に、ログを機械が辿りやすい形へ少しずつ変えていきます。

同じ事象の記録：改善前と改善後架空の例
# 改善前：どのジョブか、なぜ失敗したかが分からない
2026-09-30 10:42:05 ERROR Write failed

# 改善後：1行1JSON（JSON Lines）。イベント名・相関ID・理由コードを持つ
{"ts":"2026-09-30T10:42:05.907+09:00","level":"ERROR","comp":"spool",
 "event":"SPOOL_WRITE_FAILED","job_id":"J-20391","corr_id":"c-7f3a",
 "ver":"5.2.3","reason":"DISK_QUOTA","free_mb":0}
  • 相関ID：1つの印刷ジョブがサーバ、エージェント、DBをまたいで動くとき、同じIDを全ログに出す。案2のツールで1回の検索で全経路を追える。
  • イベント名と理由コード：文章ではなく固定の名前を出す。Drain3に頼らなくても集計できる。
  • 状態のスナップショット：容量や接続数など、障害時に知りたい値を定期的に出す。上の例の「Spool usage」はその一種。
  • ログ収集の標準化：顧客から受け取るログ一式（ファイル、期間、設定情報）を収集ツールで固定する。期間には、平常時との比較に使う障害日より前の日を含める。ダイジェスト生成の前提がそろう。

約1,000万行のコードすべてを直す必要はありません。障害が多い機能、平常時との比較でも「手がかりが足りなかった」機能から順に手を入れるのが現実的です。

評価用のデータは用意せず、実際の障害で使いながら案1から順に積み上げます。

注意点

顧客データの扱い

  • コードの外部送信は許可済みでも、顧客ログは別扱い
  • ユーザー名、文書名、PC名、IP、メールアドレスはログ収集の段階で置換する。置換は一貫させる（同じ人は常に同じ記号）と追跡できる
  • 顧客ログは障害対応の後に削除する。残してよいのはテンプレートと件数の統計だけ

複数バージョン・国別差異

  • ログ形式がバージョンで異なる場合はパーサ設定を分ける
  • 既知ノイズ辞書はバージョン系列ごとに再現環境のログから作る
  • 平常期間との比較は同じ環境の過去と比べるので、案件個別版でも基準のログを別に用意しなくてよい

平常期間の選び方

  • 前営業日に既に異常が始まっていることがある（少しずつ進む障害）
  • 問い合わせの「昨日までは正常」は事実と限らない。ログの変化点を優先する
  • 選び直した場合は理由を残す

時刻のずれ

  • サーバ・クライアント間の時計のずれ、タイムゾーンの違い
  • マージ前に正規化し、ずれがあればダイジェストに明記

根拠の確認

  • AIの結論には根拠のログ行（時刻・ファイル）を必ず付けさせる
  • 引用された行が実在するかを機械的に照合する

付録A 用語集

本文に出てくる用語の概要です。

ログテンプレートlog template / log parsing

ログメッセージを「固定の文言」と「毎回変わる値」に分けたときの固定部分の形です。たとえば Job J-20391 aborted と Job J-20392 aborted は、どちらも Job <*> aborted という同じテンプレートになります。生ログからテンプレートを取り出す処理をログパースと呼びます。

Drainログパースのアルゴリズム

2017年に発表された、ログを高速にテンプレート化するアルゴリズムです。メッセージの単語数と先頭の単語で木構造をたどって候補を絞り、似ていれば同じグループ、似ていなければ新しいグループにします。学習データが不要で、1行ずつ流しながら処理できるのが特徴です。研究でも実務でも、ログ前処理の定番として広く使われています。

Drain3Python ライブラリ

Drainを実用向けに拡張したPythonのオープンソース実装です。pip install drain3 で導入できます。主な機能は、正規表現によるマスキング（IPや数値を <IP> <NUM> に置換）、学習した状態のファイル等への保存、類似度のしきい値などの設定です。本ガイドの案1で、テンプレート集計に使います。

マスキングmasking

本ガイドでは2つの意味で使っています。1つはテンプレート化のために変わる値を記号に置き換えること（案1で行う）、もう1つは顧客情報を外部に出さないために値を置き換えること（ログ収集の段階で行う）です。

DuckDB組み込み型の分析用DB

サーバを立てずにアプリケーションの中で動く、分析向けのSQLデータベースです。SQLiteの分析版と考えると分かりやすいです。Pythonから import duckdb だけで使え、CSV・JSON・Parquetファイルを直接SQLで読めます。大量の行の集計が速く、障害1件ごとに1ファイルのDBを作って捨てる使い方に向いています。ライセンスはMITです。

Parquet列指向ファイル形式

表形式のデータを列ごとに圧縮して保存するファイル形式です。CSVより小さく、必要な列だけを速く読めます。DuckDBへの取り込み元に向いています。本ガイドの実装では、案1がDuckDBに依存しないよう、取り込み元をJSON Lines（gzip）にしました。

AIエージェントagent

AIが一度で答えを出すのではなく、「考える → ツールを使う → 結果を見て次を考える」を繰り返して課題を解く使い方です。案2の調査の流れがその例です。

ツール呼び出しtool use / function calling

AIが、あらかじめ定義された関数（検索、SQL実行など）を引数付きで呼び出す仕組みです。AIは結果のテキストだけを受け取るので、ツール側で返す量を制御できます。

SkillsAgent Skills

AIに特定の作業のやり方を教えるための、説明文（SKILL.md）とスクリプトをまとめたフォルダです。AIは作業に関係するときだけ中身を読み込みます。既存の一次調査でディレクトリ地図を渡しているのと同じ仕組みで、ログ検索の手順とコマンドを渡せます。

MCPModel Context Protocol

AIアプリケーションと外部のツールやデータをつなぐためのオープンな仕様で、2024年にAnthropicが公開しました。ツールをMCPサーバとして作ると、対応する複数のAIクライアント（VS Codeの拡張、自動実行のエージェントなど）から同じ形で呼べます。

RAGRetrieval-Augmented Generation

AIに質問する前に、関係する文書や事例を検索して一緒に渡す手法です。案3の過去障害シグネチャの照合（後回し）はRAGの一種です。

トークン・コンテキストウィンドウtoken / context window

トークンはAIが文章を処理する単位で、英数字のログ1行はおよそ数十トークンになります。コンテキストウィンドウは、AIが一度に扱える入力の上限です。上限内に収まっても、入力が長いほど費用と時間が増え、重要な情報が埋もれて精度が下がりやすくなります。

時間窓time window

分析の対象にする時間の範囲です。障害の発生時刻の前後に絞ることで、ログ量を大きく減らせます。原因が窓の外にある場合に備え、案2のツールで窓の外も調べられるようにしておきます。

平常プロファイル・平常期間baseline

同じ環境の、正常に動いていたと思われる期間（平常期間）のログの特徴です。障害時と比べ、増えたもの・減ったもの・新しく出たもの・消えたものを取り出します（ベースライン差分）。本ガイドでは案1で行います。

変化点change point

テンプレートごとの日別件数を並べたとき、「ある日から出始めた（出現）」「ある日から消えた（消失）」日のことです。少しずつ進む障害の発端を見つけるのに使います。

既知ノイズknown noise

平常時から出ているWARN／ERRORで、動作に影響がないと分かっているものです。本ガイドでは再現環境のログとソースコードからAIが辞書を作り（案3）、ダイジェストでは除外せず下に回します（案1）。

再現環境検証環境

社内で製品を動かして試験や障害の再現を行う環境です。正常に動いていたと分かっている期間のログが手に入るので、既知ノイズ辞書の元にします。障害を再現した期間は含めません。

相関IDcorrelation ID

1つの処理（1つの印刷ジョブ、1つの要求など）に付ける共通のIDで、その処理に関わるすべてのログに出力します。複数のプロセスやサーバにまたがる処理を1回の検索で追えるようになります。

構造化ログ・JSON Linesstructured logging

ログを自由な文章ではなく、項目名の付いたデータとして出す方式です。1行に1つのJSONを書く形式をJSON Linesと呼びます。パースが不要になり、DuckDBでもそのまま読めます。

階層要約map-reduce summarization

大きなログを分割してそれぞれAIに要約させ、要約同士をさらに要約する方法です。手軽ですが、途中の要約で重要な1行が落ちる危険があるため、本ガイドでは主な手段にしていません。
