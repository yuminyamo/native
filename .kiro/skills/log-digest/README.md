# log-digest（障害ログAI調査ガイド 案1 の実装）

障害ログAI調査ガイド（リポジトリの `docs/log-rca-ai-guide.html`） の「案1 ログダイジェスト生成」を Agent Skill として実装したものです。
同じ環境の正常だった期間との比較（平常プロファイル）も、そのチケットのログだけで完結するのでこの skill に含めています。
AIエージェント向けの手順は [SKILL.md](SKILL.md)、このファイルは保守する人向けの説明と残作業です。

> **現状は仮実装です。** 実際のログ例を見ずに、ガイドの架空例（INC-2026-0931）に合わせて作っています。
> 実ログで調整が必要な箇所は「[残作業](#残作業)」にまとめました。

**前提: 顧客情報のマスキングは、ログ収集の skill で先に済ませておきます。** この skill に渡されるログはマスキング済みとして扱い、
この skill ではマスキングを行いません。

## 処理の流れ（ガイドの手順との対応）

| ガイドの手順 | 実装 | 補足 |
|---|---|---|
| 1. 収集と時刻の正規化 | `parsing.py` | ファイルごとに書式・文字コード（UTF-8 / CP932 / UTF-16 を自動判定）・タイムゾーン・時計のずれを処理し、表示用タイムゾーンにそろえる。書式に合わない行は直前のレコードの続き（スタックトレース）として扱う |
| 3. マージ | `cli.py` | 全ファイルを時刻順に1本にする（同時刻はファイル順・行番号順） |
| 5. テンプレート化と集計 | `templating.py` | Drain3 に渡すのはメッセージの1行目だけ。**全期間**でテンプレート化し、窓内の件数・初出に加えて全期間の件数・初出も出す |
| 既知ノイズを下に回す | `noise.py` | 辞書（`knowledge/known_noise.yaml`）に一致したテンプレートを集計・抽出の対象から外し、ダイジェストの下に理由付きで1行ずつ残す |
| 平常時との比較 | `baseline.py` | 全日のテンプレート別件数から変化点（出現・消失）を見つけ、平常期間を選んで時間窓と比べる（下の「平常プロファイル」）。既知ノイズでも今回だけ急増・出現したものは下に回さない |
| 2. 時間窓の切り出し | `extract.py` | 申告時刻 ±30分（前後別々に指定可） |
| 4. エラー抽出と前後の文脈 | `extract.py` | ERROR 以上またはスタックトレース付きのレコードの前後5件を塊にし、重なりはまとめる。1塊は60件まで。同じ ERROR の繰り返しだけの塊は省く |
| （案2） 全レコードの出力 | `export.py` | 全期間の全レコードとテンプレートを `parsed/` に JSON Lines で書く。log-search skill が DuckDB に取り込む |
| ダイジェスト出力 | `render.py` | 目標トークン数（既定5,000）を超えたら、文脈の抜粋 → テンプレート表の行数 → スタックトレースの行数の順に削る |
| 6. マスキング | （行わない） | ログ収集の skill で実施済みの前提 |

ガイドの手順と順番が違う点は、テンプレート化を時間窓の切り出しの前に行っていることです。
窓の外でいつから出ていたログかを、テンプレート表に出すためです。

### 設計上の判断

- **決定論的にする。** 同じ入力・同じ設定からは常に同じ出力になります（テストで確認）。テンプレートID（T01 …）と塊ID（E01 …）は初出順に振ります。実行時刻は `meta.json` にだけ書きます。
- **ダイジェストのログ行は原文で載せる。** ガイドの例ではテンプレート化した文（`<PATH>` など）を載せていますが、ジョブIDやパスが残っている方が追跡の手がかりになるため、原文を載せました。
- **省略した箇所には、続きの取り方を書く。** log-search skill のツール名（`get_context ファイル:行番号` など）と、`context.md` の塊ID、`templates.tsv` を案内しています。
- **生ログはAIに読ませない。** コンテキストを使い切り、重要な行が埋もれるためです。行の確認は log-search の `get_context` で行わせます。

### 平常プロファイル（平常期間との比較・変化点）

同じ顧客環境の「正常に動いていたと思われる期間」と障害時を比べます。顧客ごとに使う機能や環境が違うので、他の環境ではなく、その環境自身の過去と比べます。

- **受け取ったログの全日を数える。** 何日分かを抜き出して調べると、変化が起きた日（架空例の9/24）を飛ばすおそれがあるためです。日数は固定せず、受け取れた分を使います。
- **変化点**: テンプレートごとの日別件数から「ある日から出始めた（出現）」「ある日から消えた（消失）」を見つけます。少しずつ進む障害は、障害日には原因のログが出ず、変化点にだけ現れることがあります。
  - 出現: 最初の3日以上は0件で、出始めた日以降の半分以上の日に出ている（1回だけのログは除く）。
  - 消失: 消えた日より前の8割以上の日に出ていて、その日から最後まで0件。障害日だけ無いものは時刻帯の違いの可能性があるので変化点にせず、平常期間との比較で扱います。
  - 判定には全日のログがある日と障害日だけを使い、ログが1件も無い日は除きます。
- **平常期間の自動選択**: 障害日より前の営業日のうち、最初の変化点より前で、ERROR が急増していない最も近い日。その日の、時間窓と同じ時刻帯と比べます。
  - 営業日はカレンダーではなく件数で判定します（中央値の半分以上）。国ごとの祝日や顧客ごとの休みを知らなくて済みます。
  - 架空例では前営業日の 9/29 ではなく、変化点（9/24）より前の 9/23 を選びます。9/29 と比べると原因の2行が「変化なし」になるためです。
  - 候補が無い時は最も近い営業日を使い、さらに前のログを依頼するよう警告します。障害日のログしか無い時は、障害日の時間窓より前と比べます（時刻帯が違うので目安）。
- **AI が選び直せる。** 障害内容・問い合わせ内容は LLM でないと読めないので、規則では扱いません。規則で選んだ期間と理由をダイジェストに載せ、合わなければ AI が `--baseline` と `--baseline-reason` で選び直します。理由はダイジェストに残ります。規則での選択を既定にしているのは、同じ入力から同じ出力になるようにするためと、問い合わせの「昨日までは正常」をうのみにして変化点を見逃さないためです。
- **比較の判定**: 障害時のみ（平常期間は0件）、消失（予想5件以上が0件）、急増（10件以上かつ5倍以上）、激減（予想20件以上が2割以下）。しきい値は `config/baseline.yaml` にあります。
- **既知ノイズは除外ではなく、下に回すだけ。** 辞書は人がレビューしない前提で AI が作るため（log-knowledge skill）、誤りがあっても原因を隠さないようにしています。平常期間より急増した、平常期間に無く5件以上出た、ある日から出始めた、のどれかに当たる既知ノイズは、今回はノイズ扱いをやめて通常のログとして扱います（`templates.tsv` の `noise_suspended` 列に理由）。

## 使い方（人が試す場合）

Python 3.9 以上が必要です（動作確認は 3.9.6 で実施済み）。

```bash
python3 -m venv .venv
.venv/bin/pip install -r skills/log-digest/requirements.txt

# 架空障害のログ（9/16〜9/30 の約14日半）を生成して試す
.venv/bin/python tests/incident_fixture.py /tmp/inc/logs      # /tmp/inc/known_noise_example.yaml も作られる
.venv/bin/python skills/log-digest/scripts/log_digest.py \
  --ticket INC-2026-0931 --incident-time "2026-09-30 10:40" \
  --product PMS --product-version 5.2.3 \
  --logs /tmp/inc/logs --known-noise /tmp/inc/known_noise_example.yaml
```

オプションの一覧は `--help` で確認できます。

## テスト

```bash
.venv/bin/python -m unittest discover -s tests
```

`tests/incident_fixture.py` が架空障害 INC-2026-0931 を模したログ（書式・タイムゾーン・文字コードをファイルごとに変えたもの）を生成し、
最初の ERROR が真の原因側（スプール書き込み失敗）になること、既知ノイズが下に回されること、出力が決定的であることなどを確認します。
平常プロファイルについては、前営業日ではなく変化点より前の 9/23 が平常期間に選ばれること、9/24 の「削除タスクの完了ログの消失」と「スキップの出現」が変化点として出ること、
既知ノイズが急増した時にノイズ扱いをやめることなどを確認します。

## skill の配置（Copilot / Kiro）

`skills/` を編集したら、次を実行してコピー結果もコミットします。

```bash
python3 tools/sync_skills.py            # .github/skills と .kiro/skills の両方へコピー

```

| ツール | 読み込む場所 |
|---|---|
| GitHub Copilot | `.github/skills/<name>/SKILL.md`（`.claude/skills/` と `.agents/skills/` も読む） |

コピー先の SKILL.md の中では、`<skill>` はそれぞれのコピー先ディレクトリを指します（例: `.github/skills/log-digest`）。
venv はワークスペースのルートに1つ作れば、どちらのコピーからも使えます。

## 性能の目安

架空の40万行（1ファイル）で約14秒、メモリ約350MB（MacBook、Python 3.9）。
14日分に散らした約42万行でも約14秒・約300MBで、平常プロファイルの処理はほとんど時間を増やしません。時間の大半は Drain3 のテンプレート化です。

時間とメモリは行数にほぼ比例します。ガイドの架空例の規模（3日で40万行）のまま1ヶ月分を受け取ると約400万行になり、
約2〜3分・約3GB の見込みです。実際の受領ログで測って、残作業10の対応が要るか判断します。

## 残作業

### 実際のログ例を見て決める必要があるもの

| # | 項目 | 現在の仮の実装 | 実ログで確認・調整すること |
|---|---|---|---|
| 1 | **ログ書式**（`log_formats.yaml`） | `2026-09-30 10:42:05.907 ERROR [spool] message` 形式と、`[component]` が無い形式の2つ。ISO 8601 のバリエーション（`T` 区切り、`Z`・オフセット付き、`/` 区切り、カンマ区切りミリ秒）は自動で読む | ファイルごとの実際の時刻形式・レベル表記・コンポーネントの有無。日付の無い時刻だけのログ、12時間表記、ロケール依存の月名など。ファイル名と書式の対応（`files` のパターン）。ローテーション後のファイル名 |
| 2 | **非テキストのログ** | 未対応 | Windows イベントログ（.evtx）、CSV、JSON Lines、zip で届くログ一式を受け取るか。受け取るならパーサを追加する |
| 3 | **複数行ログ**とトリガー条件 | 書式に合わない行は直前のレコードの続き。Java / .NET / Python のスタックトレースらしい行があれば ERROR 扱い（`parsing.py` の `STACK_LINE_RE`） | 実際のスタックトレースの形（C++ の場合など）。ERROR 以外でトリガーにしたいもの（FATAL 相当の独自表記、`Exception` を含む WARN など） |
| 4 | **文字コード・タイムゾーン** | 自動判定（UTF-16 は BOM、それ以外は UTF-8 → CP932）。TZ の無い時刻は +09:00 | 海外拠点のログ（国別差異）の TZ と夏時間。BOM 無し UTF-16 の有無。ファイルごとに TZ を変える必要があるか |
| 5 | **マスク済みログのテンプレート化** | ログ収集の skill が置き換えた記号をそのまま Drain3 に渡す | ログ収集の skill の記号の形を確認する。`<USER_001>` `<USER_002>` のように値ごとに番号が付く形だと、Drain3 が別の単語と見なしてユーザーごとにテンプレートが分かれる。その場合は `drain3.ini` の `[MASKING]` に番号付きの記号を1つの記号にまとめる規則を足す |
| 6 | **テンプレート化**（`drain3.ini`） | `sim_th=0.4`、ジョブID（`J-数字`）・パス・URL・IP・UUID・16進・数値を記号化 | 実際のID体系（ジョブID・セッションID・トランザクションID）。テンプレートがまとまりすぎる・分かれすぎる場合の `sim_th` と `depth` の調整 |
| 7 | **既知ノイズ辞書**（`knowledge/known_noise.yaml`） | 空 | 再現環境の正常期間のログから log-knowledge skill で作る |
| 8 | **既定値** | 時間窓 ±30分、前後5件、1塊60件、目標5,000トークン、最初の ERROR 3件、テンプレート表40行 | 評価データは用意しないので、実際の障害で使いながら「ダイジェストに正解の手がかりが含まれていたか」を振り返って調整する |
| 9 | **トークン数の見積もり** | ASCII 3.5文字で1トークン、非ASCII 1文字で1トークンの概算（`render.py` の `estimate_tokens`） | 実ログのダイジェストを、利用するモデルのトークナイザで数えて係数を合わせる |
| 10 | **性能** | 40万行で約14秒・300〜350MB（全レコードをメモリに持つ） | 2週間〜1ヶ月分を受け取ると、実ログでは数百万行になりうる（下の「性能の目安」）。メモリが足りなければ、平常期間の候補と障害日だけ全レコードを持ち、ほかの日は件数だけ数える形に変える（ただし log-search で全期間を検索できるよう、parsed/ への書き出しは全件のまま） |
| 11 | **平常プロファイルのしきい値**（`baseline.yaml`） | 営業日は中央値の半分以上、変化点は3日以上の履歴、比較は上記の判定 | 実ログで、変化点が多すぎる（毎日少しずつ違うログが多い）・少なすぎる場合に調整する。週1回・月1回の処理が「出現」に見えないか |
| 12 | **時間帯単位の平常期間** | 日単位の選択だけ（AI が `--baseline` で範囲を指定することはできる） | 平常期間の日の中の異常な時間（夜間の再起動など）を規則で除く必要があるか |
| 13 | **件数の水準の変化・値の推移** | 変化点は出現・消失だけ。使用率などの値の推移は見ない | 「ある日から件数が5倍になった」「使用率が単調に増えている」を変化点として出す必要があるか |
| 14 | **平常期間の自動選択の妥当さ** | 最初の変化点より前で ERROR の急増が無い最も近い営業日 | 実際の障害で、AI が `--baseline` で選び直した頻度と理由を集める。多ければ規則（変化点の扱い、ERROR 急増の判定、曜日をそろえるか）を見直す |
| 15 | **受領ログ一式の構成** | ディレクトリを再帰的にたどり、`*.log` `*.log.*` `*.txt` だけを読む | 実際に届くディレクトリ構成・ファイル名。設定ファイルや診断情報など、ログ以外に読むべきファイルがあるか |

### 他の案との接続

- **案2 ログ検索ツール**: [log-search skill](../log-search/README.md) として実装済みです。この skill は `parsed/` に全レコードを書き出すだけで、DuckDB への取り込みと検索は log-search が行います（log-digest は duckdb に依存しません）。
- **案3 環境をまたいで残す知見**: [log-knowledge skill](../log-knowledge/README.md) が既知ノイズ辞書（`knowledge/known_noise.yaml`）を作り、この skill が読みます。
  log-knowledge は、再現環境のログをこの skill にかけた出力（`parsed/` と `meta.json` の `baseline.days`）から候補を作ります。`meta.json` の形を変える時は log-knowledge 側も確認します。
- **案4 ログ自体の改善**: JSON Lines のログが出てきたら、正規表現ではなく項目名で読むパーサを `parsing.py` に追加します。
